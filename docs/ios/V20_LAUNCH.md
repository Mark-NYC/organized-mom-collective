# Organized Family V20: production launch (2026-11-27)

V20 (the locked baseline, [V20_BASELINE.md](V20_BASELINE.md)) is the production experience at **/app** on the website, running on each signed-in household's real data. There are no feature flags, no parallel experience and no fictional data. This file records what was launched, how it works, how to roll it back, and what remains.

## 1. What is live

| Route | What it is |
| --- | --- |
| `/app` | The V20 Today on the household's real data. Short headline, at most one light brown card, What matters (priorities, the family's own focus, activities with their preparation, earlier days receded), Everyone's part, the Family Meeting row, and Plans · Cleaning · Resources. "Something changed?" is the quiet link under the headline. |
| `/app/family/meeting` | The V20 Family Meeting: Our Focus → Let's Talk (the month's questions, ideas, the agenda Today routed here) → Everyone's Part (Keep / Change / Skip / We agree; prepared suggestions from the family's real calendar, the Club month, ideas) → Let's Practice (development records, Club), the week-four check-in, and the plan. |
| `/app/cleaning` | The V20 cleaning view on the household's shared marks and rhythm (from the foundation work), with the shared status line restored. |
| `/app/account` | Unchanged account, family and billing, plus V20's Notifications (three purposes, the Family Meeting reminder, quiet hours), This device (Web Push on/off), heads-ups on Today, and what we've learned (correctable). |
| `/app/family-calendar`, `/app/family`, sign-in, invitations, Club | Unchanged real pages, in the V20 chrome (two-tab floating navigation). |

The previews (`/preview/organized-family-v16` … `v20`) stay unlinked and `noindex` as design references.

## 2. How it is wired (no rewrite: the existing stores stay the source of truth)

```text
real stores ──► liveState() ──► the approved V20 screens ──► writesFor() ──► the same real stores
```

The mapping lives in `src/lib/v20/live.ts`; `src/components/v20/LiveFamily.tsx` runs it.

| V20 concept | Real store |
| --- | --- |
| Agreed parts ("We agree", edits, re-agree) | Agreements: offline outbox, revision-checked (`household_agreement_save`) |
| Preparation on imported events (checkbox shared by both adults) | Event responsibilities (`calendar_event_task_*`) |
| What matters | `household_priorities` |
| Let's Practice | Development records (`household_development_decide`), Club only |
| Resume, finished | Shared meeting checkpoint (`family_meeting_progress`) |
| Cleaning boxes, one-week moves | `household_cleaning_marks`, `family_cleaning_rhythm` |
| Activities | The family calendar and the connected calendars this adult may see. Private ones are only theirs |
| Memory, feedback, reports, completion history, what was shown, topics, claims, notification preferences, suggestions and handoffs not yet agreed, V20 details of agreements | **`household_intelligence`** (new): one revision-checked document per household. Devices merge three ways (`src/lib/v20/intel-sync.ts`), so two adults never overwrite each other |

**Notifications.** The locked rules in `src/lib/v20/notify.ts` run on each device over the shared plan. Each result is queued with `household_notify`, which keeps one row per household and dedupe key, so two phones send it once. The pg_cron job `omc-household-push-dispatch` runs every minute and hands due rows (including those held for quiet hours and scheduled meeting reminders) to the Edge Function `push-delivery`, which sends Web Push.

The service worker (`public/sw.js`) shows each notification with "I've got it" / "Not this time". Tapping one opens `/app`, which applies it as the signed-in adult (`gotIt` / `notTonight`) and updates the shared plan on every device.

**Push keys.** The VAPID key pair was generated by `push-delivery` itself and lives in `household_push_keys`, readable by the service role only. The private key never left Supabase. Browsers read the public key through `household_push_key()`.

**Calendar links.** When an adult opens the app, their own iCal links that are more than six hours old are refreshed, through the same signed-in call as "Refresh" in Plans.

**Intelligence.** Fully deterministic: playbooks, memory, attention routing and timing. There is no model provider. The simulated interpreter from the previews never runs on live data (`ctx.s.live`).

## 4. Rollback

1. **App:** in Cloudflare Pages, redeploy the production deployment before the launch merge (`main` at `55b7693`, PR #531's merge). The previous app ignores every new table.
2. **Calendar switches, if needed:** `update public.calendar_feed_rollout set everyone = false, event_tasks_everyone = false where id;`
3. **Notifications, if needed:** `select cron.unschedule('omc-household-push-dispatch');` stops all delivery at once.
4. **Data, only if required:** the drop statements are at the end of each migration file. Keep `household_intelligence` when rolling back the client so a family's learned state can be restored. Full database restore: [DATABASE_BACKUPS.md](../operations/DATABASE_BACKUPS.md), from the VERIFIED backup above.

## 6. Not in this launch (documented, not simulated)

- **Native iPhone push (APNs).** The web launch uses Web Push.
  - It works on Android and desktop browsers, and on iPhone (iOS 16.4+) only when Organized Family is added to the Home Screen. Account says so.
  - The native app still needs the Apple Push Notification service: an Apple key, `@capacitor/push-notifications`, a `HELP` category with the two actions, and a native branch in `push-delivery`.
- **Google Calendar for everyone.** It needs Google's OAuth verification (owner action; [GOOGLE_CALENDAR.md](../calendar/GOOGLE_CALENDAR.md)). Calendar links (iCal) are on for everyone.
- **A real event interpreter.** No provider is selected. Today runs on the deterministic rules, as the V18 audit intended.
- **Scheduled server-side calendar refresh.** It needs the owner-set secret in [ROLLOUT.md](../calendar/ROLLOUT.md) Stage B. Until then, links refresh when their adult opens the app.
- **Device-level verification of Web Push delivery.** A notification has to be received on a physical phone (an installed PWA on iPhone, Chrome on Android). The server side is verified: the queue, dedupe, dispatch, the function and the keys.
